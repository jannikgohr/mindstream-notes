# Editor experience and behavior specification

Audit date: October 27, 2026.

This document defines the writing experience wanted for Markdown notes on desktop
and mobile. Each behavior has a stable ID, a trigger, a wanted result, and an
unwanted result so it can become one or more test cases. It covers both the rich
editor and the source editor. It does not select a replacement editor or implement
any of the proposed changes.

The priority is a rich writing experience at least as good as the current
Milkdown editor. Source editing must work without losing text or unexpectedly
rewriting unrelated parts of the note.

## Source preservation contract

Rich editing may reserialize the Markdown block being edited. Its marker style,
spacing, escaping, or line wrapping may change as a result. Character-for-character
preservation inside that edited block is not required. Its content and intended
formatting must survive.

For this specification, a block is a top-level Markdown paragraph, heading, list,
blockquote, fenced code block, table, or opaque source block. Editing one list item
may reserialize that enclosing list. Editing one table cell may reserialize that
table. Preserving individual list items or table cells more precisely is welcome,
but is not a requirement. Separate lists, tables, and paragraphs remain unrelated
blocks. A paragraph inside a list is not permission to reserialize another list.

Splitting, joining, moving, deleting, pasting over, or applying formatting across
several blocks may change every block directly involved in that operation and the
separators required to express the resulting structure. Source outside that set,
including independent definitions, comments, and surrounding blank-line runs,
stays unchanged. An intentionally shared reference definition is an additional
affected block only when the action explicitly changes that definition.

Opening a note, selecting text, moving the caret, focusing a block, changing view
mode, rendering a preview, autosaving, receiving presence, and resizing the window
are not content edits. They grant no permission to normalize source. A remote rich
edit has the same affected-block boundary as a local rich edit. A block containing
concurrent source changes must be normalized from its merged content, never from
an older snapshot that omits those changes.

Source editing preserves the characters the user enters, including incomplete or
unsupported syntax, until a deliberate rich edit affects that block. A parser
must not turn a temporarily incomplete construct into destructive source edits.
An explicit format-document command may have a wider scope, but ordinary editing
must not behave like that command.

## How to read the audit

- **Confirmed gap** means the implementation contradicts the wanted behavior.
  Findings below distinguish code evidence from a browser reproduction.
- **Guard exists** means the app already implements the behavior or has a
  regression for it. It is a requirement to retain, not a new defect claim.
- **Verify** means the behavior needs a focused test or device session. Missing
  test coverage is not evidence that the feature is broken.
- **Proposed** means a product improvement rather than a demonstrated defect.
- **P0** protects content, composition, collaboration, and undo correctness.
- **P1** covers everyday writing, navigation, formatting, and mobile interaction.
- **P2** covers optional comfort features and performance targets requiring a
  recorded device baseline.

The catalog describes wanted product behavior. The reference applications supply
specific precedents, not a claim that every application implements every row.

underlying text, not DOM `innerText`, which can misrepresent blank lines or omit

## Fixtures and boundaries for later tests

Use a small fixed fixture set rather than a different ad hoc document per test.

- **Mixed source.** At least five top-level blocks with `+` bullets, `~~~` code,
  `__strong__`, reference-style links and separate definitions, HTML comments,
  front matter, intentional blank-line runs, trailing hard-break spaces, and a
  final-newline variant. Edit a marked middle block, then compare every other
  source slice exactly. Test logical text preservation separately from on-disk
  encoding and LF/CRLF preservation.
- **Structure.** Nested mixed lists with completed/empty tasks, a blockquote,
  two adjacent distinct tables, an image, inline code, and a terminal code/table
  block. Record expected semantic content before testing normalization.
- **Unicode and composition.** Latin dead-key accents, decomposed accents, Arabic
  or Hebrew beside Latin text, CJK IME input, emoji with skin tones, flags, and ZWJ
  sequences. Synthetic key events do not replace a real IME session.
- **Collaboration.** Two clients with controllable delivery and offline periods.
  Cover rich/rich, source/source, and both source/rich orientations, in different
  blocks and the same block. Add desktop/mobile pairs and reorder, repeat, and
  delay update delivery. Reopen persisted documents before asserting completion.
- **Long note.** Record exact fixture size and shape. Start with approximately
  100,000 characters of prose and a second mixed-content document near 1 MiB.
  Include wrapped lines, 50 tables, and code blocks in the mixed fixture. Measure
  cold open separately from steady-state typing and from the first edit after a
  remote update.

For COM-04, initial investigation targets are p95 input-to-next-paint below 50 ms
on the reference desktop and 100 ms on the reference phone during steady-state
typing. These are proposed engineering targets, not measured current performance
or universal hardware promises. Record device, OS, WebView/browser, refresh rate,
power mode, fixture, and measurement method before making them release gates.

For asynchronous behavior, wait for an observable result such as committed
content, a completed upload, a save acknowledgement, or converged state. Avoid
making a test pass by adding a delay before the first character of a newly
created block. Test inputs on both sides of debounce boundaries deliberately.

Each future test should record the initial source, visible surface, document
selection, input method, settings, action, expected source changes, expected rich
structure, final caret/selection, undo result, and persistence/sync result where
relevant. Split rows into several tests when they cover distinct input methods or
structural contexts. Keep the behavior IDs stable when implementation changes.

## Audit validation and limits

The implementation review covers `NoteEditor`, `SourceEditor`, Crepe setup, source
commands, toolbar routing, pairing, typeahead, diagnostics, search, presence,
save scheduling, the existing editor browser suites, and the documented history
and sync limitations.

All 42 existing Chromium regressions in the following focused run passed:

```sh
pnpm test:e2e editor-menus.spec.ts editor-view-modes.spec.ts \
  markdown-roundtrip.spec.ts mobile-editor-stability.spec.ts \
  --project=chromium --workers=2
```

Separate, temporary browser probes reproduced these failures against the same
production frontend build:

- **G01.** Entering `+ first`, `+ second`, and a `~~~js` fenced block in Source,
  then switching to WYSIWYG and back without rich editing, returned `-` list
  markers, backtick fences, and an added final newline.
- **G02.** Starting with `BASE` in Split, inserting ` LATEST` in Source, and
  immediately invoking the WYSIWYG mode toggle returned rich text `BASE` after
  the debounce interval. The last source edit was lost.
- **G04.** Finding `#` in source containing `# Heading` reported no results.
  Closing Find left `document.activeElement` on the page body, outside Source.
- **G06.** The Source toolbar's Table action inserted ` | |` as the header line
  above a two-column delimiter row. Switching to WYSIWYG produced zero tables.
- **G07.** Selecting two paragraphs containing one bold span and typing `(`
  changed the result to one paragraph with no bold spans and text
  `(first bold\nsecond)`.
- **G14.** Choosing Bullet List with a normal pointer click, then typing without
  a component-settling wait, reordered all five sample strings. `Sample0` became
  `ample0S`; other samples included `mple1Sa` and `ple4Sam`.

Direct probes of the actual exported source-command functions also reproduced
G05: toggling bold on the label in `__word__` produced `__**word**__`; applying a
heading to `[0, 4)` in `One\nTwo` produced `# One\n# Two`. A GFM parser classified
the inserted table from G06 as a paragraph, independently of the browser result.
These are audit reproductions, not committed regression tests or implemented
fixes. A further browser probe confirmed G13: Enter in an unmatched `[[query]]`
inserted no newline in either surface; the rich popup remained visible.

The successful existing regressions and these failures are consistent. The
existing suite verifies canonical Markdown and common UI paths. It does not
establish the stronger source-preservation contract, every source command, or
the fast switch before the source debounce expires, or immediate input during
new list component mounting.

No native mobile/IME, real two-client backend, screen-reader, or cross-application
clipboard session has been run for this audit. Those rows remain verification
work even if their browser equivalents pass.

The T3 preview browser is unavailable on this host because its sandbox is blocked
by AppArmor. Browser checks use the repository's documented Playwright workflow
from [the E2E guide](../../e2e-tests/README.md). Browser-fallback storage is an
in-memory mock, so these checks do not establish native persistence or live sync.
